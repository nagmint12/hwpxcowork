# MCP 얇은 흐름(lean) — 요청 한 건의 왕복과 글자 수 줄이기

2026-11-10. 질문은 세 가지였다: ① 작업 종류를 먼저 분류하고 그 종류의 지침만 내려주는 2단 구조가 더 빠른가 ② 그것이 병목이라면 어떻게 체계화할 것인가 ③ 문서를 통째로 '파일'로 넘기는 편이 나은가. 이 문서는 실제 대화 기록의 측정, 결론, 바꾼 구조, 전후 측정, 켜는 방법을 적는다.

> **2026-11-17 뒤의 자리**: lean 은 **예전 연결(v1)의 모델용 변형**이다. 2026-11-17 사용자 결정으로 서버 `/mcp`·브리지·`setup-agent`·실행기의 기본은 새 연결(v2 — 작업 도구 넷 `task`·`read`·`edit`·`finish`, [연결과 대기열 안내](AGENT_SETUP.md#12-chatgptcodex-연결과-대기열) §13)이다. lean 은 밝힐 때만 쓴다 — 머리글 `X-Hwpx-Lean: 1`·주소 `?lean=1`·브리지 `--lean`(`--v2` 가 없으면 예전 연결). `setup-agent` 는 `--v1` 일 때만 브리지에 `--v1 --lean` 을 넣는다. 이 문서 본문의 '기본 연결'은 그때(11-10)의 기본, 곧 지금의 '예전 연결(v1)'을 뜻한다. 아래 기록은 그때의 사실이라 고치지 않았다.

**상태**: 코드 수정·로컬 검증·운영 반영. 2026-11-10 10:19 KST 운영 서버(:8787)를 정상 재시작했고 10:21 관리자 채널 에이전트를 `--lean` 으로 시작했다(사용자 지시 — 7절). 운영 서버에서 읽기만으로 기본 연결(도구 61개, `complete` 없음)과 lean 연결(60개, `complete` 있음)을 확인했다. 실제 모델을 부른 전후 비교는 아직 없다 — 아래 전후 수치는 모델 없이 잰 글자 수와 호출 수이고, 실제 요청이 쌓이면 1절의 스크립트로 다시 잰다.

## 1. 실제 흐름에서 잰 것(2026-11-09 관리자 채널 에이전트, Claude Code)

`scripts/agent-transcript-stats.mjs` 로 채널 세션 기록 한 개(요청 9건 — 낱말 고치기·메모 답장·차례 새로 고침 3종 × 3회)를 숫자로만 뽑았다(`artifacts/mcp-lean-flow-20261110/channel-transcript-20261109.txt`).

| 항목 | 값 |
|---|---|
| 요청 한 건의 모델 호출 | 4~8회(합계 48회) |
| 그중 실제 편집 호출 | 요청마다 1회 — 나머지는 `get_request`·`start_request`·`complete_request`·도구 찾기·마무리 글 |
| 세션 문맥(모델이 호출마다 다시 읽는 양) | 첫 요청 41,670 → 아홉째 요청 뒤 127,113토큰(요청마다 약 7.5천 토큰씩 쌓임) |
| 9건의 입력 합계 | 4,502,111토큰(캐시 읽음 4,408,231 · 캐시 씀 93,764 · 새 입력 116), 출력 10,536 |
| 낱말 하나 고치기(선택 17자·지시 18자)의 도구 응답 | `get_request` 3,861자 + `start_request` 1,492 + `propose_changes` 533 + `complete_request` 1,933 = 7,819자 |
| 그 요청의 실제 내용(지시·대상·앞뒤 문단) | 300자 안팎 |
| `get_request` 3,861자의 구성 | 할 일 안내(`howTo`) 1,135 · `contextItems` 687 · `context`(같은 글) 218 · 그림 목록 181 · 서식 안내 161 · 해결 통계 142 … |

읽는 법: 캐시가 값을 깎아 주지만(읽기 0.1배) 호출 수와 문맥 길이는 그대로 시간과 한도를 쓴다. **비용 = 호출 수 × 그때의 문맥 길이**이고, 요청의 실제 내용은 그 안에서 아주 작다. "간단한 수정도 모든 내용을 받는다"는 느낌의 정체는 세 가지였다 — (a) 모든 종류의 작업 요령을 담은 `howTo` 가 요청마다 온다 (b) 맡기·완료 도구가 요청 전체(이력·선점·통계)를 되돌려 준다 (c) 그 모든 것이 세션에 쌓여 다음 요청의 모든 호출이 다시 읽는다.

## 2. 결론

1. **'분류 → 지침' 을 모델 단계로 따로 두면 더 느리다.** 단계 하나 = 모델 왕복 하나이고, 왕복마다 문맥 전체(4만~12만 토큰)를 다시 읽는다. 지금 흐름에서 줄여야 할 것이 바로 그 왕복이다. 그리고 2026-11-04~05 에 같은 구조(기능 선택 plan/execute, 단문 전용 경로)를 넣었다가 뺐다 — 단순 요청은 입력이 90% 넘게 줄었지만 「시사점·정책제언 + 표·그림 번호 + 차례」 같은 복합 요청이 분류에 걸려 실패했다(`old/docs/EDIT_RUNTIME_PLAN_2026-11-05.md`·`old/docs/CHANNEL_EDITOR_RESTORE_2026-11-05.md`). 분류가 틀리면 능력이 사라지는 구조는 정확도를 깎는다.
2. **그 생각의 알맹이(필요한 지침만)는 왕복 없이 구현한다 — 지침을 세 층으로 나눈다.**
   - 1층(요청마다, 아주 짧게): 요청 내용 + 한 줄짜리 도구 색인. 모든 능력의 이름이 늘 보이므로 AI 가 고른다(도구를 좁히지 않는다).
   - 2층(AI 가 그 도구를 고르는 순간 따라온다): 도구별 자세한 규칙은 그 도구 설명에 둔다. 도구 정의는 늘 같은 앞부분이라 캐시된다 — 왕복이 들지 않는다.
   - 3층(드문 일을 할 때만 읽는다): 긴 절차 — 표준서식 작성 지침(`get_writing_guide`), 그림 파일 고치기·멀티에이전트·변경 요청 검토(`agent/guides/*.md`). 여기서만 '하겠다고 하면 지침을 받는' 한 번의 읽기를 치른다.
   - 서버가 지시 글을 보고 덧붙이는 것은 **도움말뿐**이다(그림·표·첨부가 보이면 그림 목록과 파일 절차 한 줄). 틀려도 잃는 것은 도움말 한 줄이고 도구는 그대로 있다.
3. **파일로 통째 넘기는 것은 편집에는 맞지 않는다.** 파일을 읽으면 그 글이 그대로 문맥에 들어가므로 작은 수정에서는 지금(대상 + 앞뒤 2문단, 수백 자)보다 훨씬 많이 읽는다. 문단 주소(ref)·find 로 묶인 제안·변경 추적·동시 편집 보호도 잃고, ChatGPT·API 연결은 내 PC 파일을 읽지 못한다. 문서 전체가 필요한 일(전체 검토·톤앤매너)은 지금도 한 번에 온다(문서 전체 대상 요청 = 그 범위 글, `read_document` 한도 4만 자). 파일 경로가 뜻이 있는 곳은 로컬 에이전트가 문서를 크게 다시 짜는 일이고, 그것은 변경 요청으로 받는 별도 길(`docs/MCP_TOOLSET_PLAN_2026-11-03.md` 의 파일 레인)로 남겨 둔다.

## 3. 바꾼 구조 — 얇은 흐름(lean) 연결

모델이 직접 읽는 MCP 연결이 `lean` 을 켜면 서버가 같은 도구로 짧게 답한다. **도구는 그대로 다 준다.** 켜지 않은 연결(개인 실행기·옛 클라이언트·기존 시험)은 응답 꼴이 한 글자도 바뀌지 않는다.

| | 기본 연결 | lean 연결 |
|---|---|---|
| 켜는 법 | — | 브리지 `--lean`(머리글 `X-Hwpx-Lean: 1`) 또는 주소 `…/mcp?lean=1` |
| 요청 받기 | `get_request` → `start_request` (2회) | `start_request` 하나 — 맡으면서 요청 내용을 함께 준다(`claim_next_request` 도 같다) |
| 요청 내용 | 전체 자료(`contextItems`·`context`·통계·긴 `howTo` …) | 지시·대상·문맥 줄(`*[ref] 〔스타일〕 글`)·대상 표·첨부·짧은 `howTo`. 서식 번호·값은 서식이 필요한 요청에만(`formatting`) |
| 끝내기 | 쓰기 → `complete_request` (2회) | 마지막 쓰기에 `complete="요약"` — 저장이 모두 된 뒤에만 완료한다(실패한 항목이 있으면 완료하지 않고 알려 준다) |
| 쓰기·완료 응답 | 제안·요청 전체(이력·작성자·보낸 글의 되풀이) | 영수증(`pid`·`status`·`ref` …, 실패 항목의 오류 글은 그대로) |
| 도구 정의 | 61개 73,071자 | `null` 허용 가지·값 범위를 뺀 스키마, `propose_changes` 와 같은 `propose_change` 는 목록에서만 뺌(부르면 된다) — 54,107자 |

- 구현: `server/lean.js`(순수 함수 — `leanRequest`·`leanReceipt`·`leanToolSchema`), `server/mcp.js`(`createMcpServer({ lean })`), `server/index.js`·`mcp-modern.js`(연결의 lean 값), `server/bridge.js`·`mcp-stdio.js`(`--lean`, lean 용 채널 안내·알림 글).
- 선점·취소·시도 번호·권한 검사는 그대로다(`complete` 는 같은 세션·같은 시도로 `completeRequest` 를 부를 뿐이다). 결과 없이 완료할 수 없는 것(`NO_RESULTS`)도 같다. 자동 반영 문서는 완료하면서 제안이 반영되므로 영수증에는 완료 뒤의 상태(`applied`)를 싣는다 — 요청·제안 상태, 본문, 문서 판은 기본 연결로 처리했을 때와 같다(독립 확인).
- 섞인 상태도 된다: 새 브리지 + 옛 서버 = 옛 응답 꼴(에이전트 지침이 "내용이 없으면 `get_request`" 로 받는다), 옛 브리지 + 새 서버 = 기본 연결.
- **API 실행기**(개인 키·서버 AI — OpenAI·Claude·Gemini)는 연결을 바꾸지 않고 모델에 넘기는 쪽만 같은 함수로 줄였다(`server/api-mcp-tools.js`): 도구 스키마 48,241 → 36,531자, 쓰기 도구 결과는 영수증. 그리고 표준서식 작성 지침(약 3천 자)을 요청 글에서 시스템 지시로 옮겼다(`server/ai.js` `systemText` — 요청마다 제값으로 읽히던 글이 캐시되는 앞부분이 된다. 글 자체는 같다).
- **채널 에이전트 작업 공간**: `agent/CLAUDE.md` 8,609 → 5,555자. 그림 파일 고치기·멀티에이전트·변경 요청 검토 절차는 `agent/guides/` 로 옮기고 그 일을 할 때만 읽게 했다(읽기만 허용, 고치기 거부).

## 5. 하지 않은 것

- 사람이 고른 요청 종류나 지시 낱말로 **도구를 좁히지 않았다**(2026-11-03 결정 그대로).
- 기본 연결의 `get_request`·`start_request`·`claim_next_request`·쓰기 응답은 바꾸지 않았다 — 배포된 개인 실행기 ZIP 이 그 꼴에 기댄다.
- Codex 실행기(stdin 으로 넘기는 요청 자료)와 Gemini CLI 경로는 그대로다. 같은 함수(`leanRequest`)를 쓰면 되지만 실제 구독 모델로 확인한 뒤에 바꾼다.
- 채널 알림에 요청 내용을 싣지 않았다 — 알림 글에는 번호만 싣는다는 계약(V3 §2.3)을 지켰다.

## 6. 남은 큰 것(결정이 필요)

1. **세션에 쌓이는 문맥 — 일하는 동안은 두고, 쉬는 동안 요약한다(2026-11-10 사용자 결정 → 같은 날 적용, 9절)**: 채널 세션은 요청이 끝나도 앞 요청들을 계속 들고 간다(1절 — 9건 뒤 12.7만 토큰). 같은 문서에서 이어지는 작업에는 앞 문맥이 더 좋은 답을 내는 데 도움이 되지만, 보내는 요청마다 끝없이 쌓을 필요는 없다는 것이 사용자의 판단이다.
2. Codex 실행기의 요청 자료를 `leanRequest` 로(실제 구독 모델 확인 필요).
3. 개인 실행기가 요청 한 건에 `get_request` 를 5번쯤 부르는 것(모델 토큰은 아님 — 서버 일).
4. ChatGPT(Work) 커넥터는 주소를 `…/mcp?lean=1` 로 다시 등록해야 lean 이 된다.

- 12만의 근거: 새 세션이 도구를 불러온 뒤 약 6만 토큰이므로 그 두 배 — lean 요청(한 건에 약 3~4천 토큰) 열 건 남짓을 이어 작업할 여유가 있고, 문서 하나를 통째로 읽은 뒤(오늘 17만)에는 쉬는 동안 반드시 줄어든다. 요약 한 번의 값(전체를 캐시에서 한 번 읽고 요약을 쓰고 줄어든 문맥을 새로 캐시에 씀)은 다음에 캐시가 식은 뒤 첫 호출이 큰 문맥을 통째로 다시 쓰는 값보다 작다.
