사용자 요구(원문 요약, 2026-10-23)
1. 내가 친 글과 남이 친 글이 **실시간으로** 서로에게 보인다. 타이핑과 동시에 반영되고, 관리자가 따로 승인하는 절차는 필요 없다.
2. **검토본·최종본 등으로 나뉜 것을 하나로** 합친다('한글로 저장' 단추 하나 — 무엇을 담을지는 문서 설정).
3. 문서에 **수정 권한**이 있으면 바로 고칠 수 있다. 이것을 **문서 설정**으로 고른다 — **승인(허용) 방식**과 **실시간 수정 방식** 둘 다 있어야 한다. 실시간으로 고친 글을 변경 추적으로 남길지도 **문서별 설정**.
4. 다른 사람이 화면에 들어오면 변경 요청·검토가 너무 많아 **자기가 검토해야 하는 것처럼** 느낀다. AI 작업은 지시한 뒤 고친 내용을 **간략히**(예: 「회의록의 회의일자를 2026. 10. 21.(수)로 바꾸고, … 확인이 필요하다는 메모를 남김.」) 보여 주면 된다. 자세한 변경 내역은 서버(이력)에 있으면 되고, 기본 화면에 메모·변경·검토 같은 옵션이 너무 많지 않게.

사용자가 고른 것(2026-10-23 질문 답)
- 실시간 문서에서 **수정 권한이 없는 사람 = 읽기·메모·AI 요청만**(편집기는 읽기 전용).
- 실시간 문서의 **AI 결과 = 요청한 사람이 보고 반영**([모두 반영]·하나씩) — 반영하는 즉시 공유 문서에 들어가 모두에게 보인다(관리자 승인 없음). 다른 사람에게는 한 줄 요약만.
- 실시간으로 고친 글을 **변경 추적으로 남길지 = 문서별 설정**(고친 글만 / 변경 추적으로).
- **'한글로 저장' 하나**에 담을 것 = **문서별 설정**(보이는 그대로 + 메모 / 변경 추적 포함 + 메모).

## 1. 문서 설정(`meta.settings`)

```js
settings: {
  editMode: 'realtime' | 'review',   // 편집 방식: 실시간 수정 | 승인 후 반영(v0.3 수정본·변경 요청 — 이름은 '승인 방식')
  editors: 'all' | string[],         // 수정 권한: 편집자 모두 | 지정한 사람(이름 목록)
  track: 'final' | 'tracked',        // 실시간 수정 기록: 고친 글만(변경 추적 없음) | 변경 추적으로(작성자별)
  exportKind: 'final' | 'tracked',   // 한글로 저장: 보이는 그대로(최종 글) + 메모 | 변경 추적 포함 + 메모
  aiMemo: 'summary' | 'detail' | 'none', // AI 작업 메모: 요약만 | 요약 + 반영 목록 | 신규 자동 기록 생략
  aiQuick: 'send' | 'compose',       // AI 빠른 작업: 누르면 바로 보내기 | 요청 창에서 확인 후 보내기(화면만 쓴다 — §5, 2026-10-28)
}
```
- 기본값: `{ editMode: config.documents.defaultEditMode ?? 'realtime', editors: 'all', track: 'final', exportKind: 'final', aiMemo: 'summary', aiQuick: 'send' }`(`_settingDefaults`·`_normSettings`). `settings` 가 없는 옛 문서는 `_norm` 이 이 기본값으로 채운다(사용자 config 에는 `documents` 구역이 없다 → 옛 문서도 실시간·빠른 작업은 바로 보내기). 모르는 값은 기본값으로. 서버 config 만의 덧붙임 `documents.defaultTrack`·`defaultExportKind`·`defaultAiMemo`·`defaultAiQuick` 도 같은 식으로 읽는다(§8-1).
- **수정 권한** `canEdit(user, meta)` = 관리자이거나, 역할이 `viewer` 가 아니고 (`editors === 'all'` 이거나 `editors` 에 그 이름이 있음). 에이전트(`사용자(에이전트)`)는 그 사용자의 권한. 역할 `viewer`(config users 의 `role`)는 어디서나 읽기 전용 — 새로 받는 역할값(없으면 editor 그대로).
- **설정 바꾸기**: 관리자 또는 문서를 올린 사람(`meta.createdBy`). `PATCH /api/docs/:id/settings { editMode?, editors?, track?, exportKind?, aiMemo?, aiQuick? }` → `{ settings }`(검사: 값 목록, `editors` 는 `'all'` 이나 이름 배열(200명·이름 100자까지, 중복 제거 — config 에 없는 이름도 받되 경고 없음)); 그 밖 403 `FORBIDDEN`, 400 `BAD_SETTING`. meta 만 고친다(기록·버전 없음, 문서 큐 안). `store.log(meta, by, 'settings', …)`. WS `{ type: 'doc', action: 'settings', settings, by }`.
- `GET /api/docs`·`GET /api/docs/:id`(`_summary`) 에 `settings` 와 `canEdit`(부른 사람 기준)·`canConfigure`(설정을 바꿀 수 있는가). `GET /api/users` → `[{ name, role }]`(로그인한 사람 누구나 — 토큰은 절대 싣지 않는다; 설정 창의 사람 고르기).
- MCP `list_documents`·`read_document` 응답(문서 정보)에도 `settings`·`canEdit`. 에이전트의 '기준 바꾸기'(`apply_proposal`) 문은 §4.3.

## 2. 실시간 수정(`editMode: 'realtime'`)

### 2.1 무엇이 달라지나
- 편집기에서 친 글은 **곧바로 공유 기준 문서**에 들어간다(내 수정본·변경 요청·승인 없음). 다른 사람 편집기에는 1~2초 안에 보인다(아래 2.4 — 그 사람이 치는 중이면 손을 멈출 때).
- 수정 권한이 없는 사람의 편집기는 **읽기 전용**(플러그인 `setOptions({ readOnly: true })` §2.5). 메모 달기·답글·AI 요청은 된다.
- 기준 문서의 '기록'(내부 판 n)은 밀어 넣기(§2.2)마다 하나 생긴다(V3 §9.1 — 사람용 버전 v 는 오르지 않는다). 버전은 [버전 저장]·복구·AI 작업 해결(새 적용)·문서 올림 때만(V3 §9.4 그대로).
- 승인 방식(`review`)은 v0.3 그대로(수정본 → 변경 요청 → 승인 → 반영). 두 방식 모두 REST 의 수정본·변경 요청 API 는 그대로 받는다(옛 클라이언트·에이전트) — 웹이 방식에 따라 쓰는 길만 다르다.

### 2.2 밀어 넣기(클라이언트 → 서버) — `PUT /api/docs/:id/live?base=<n>&seq=<k>&loaded=<L>` (본문 HWPX = 편집기 내보내기)
- 웹 편집기: 'edited' 뒤 **쉼 800ms**(쳐도 **3초**마다 한 번) → `exportHwpx()` → PUT. 한 번에 하나(진행 중이면 끝난 뒤 남은 것을). `base` = 편집기 기준 기록 n(setBase 의 version), `seq` = 이 창의 밀어 넣기 차례(진단용).
  `loaded`(2026-11-04) = 편집기 문서를 연 작업본의 판. 편집기는 메모만 바뀐 판(남이 단·지운 메모, AI 작업 메모)을 다시 열지 않고 기준만 옮기므로(§2.4) 편집기 문서의 메모는 기준 판이 아니라 연 판의 것(+ 이 창이 밀어 넣어 바꾼 것)이다. 서버 메모 맞추기(`server/live.js` `liveMemoPlan`·`_memoKnown`)는 이 메모(창마다 지난번 밀어 넣은 문서의 메모, 처음이면 `versions/<L>.hwpx` 의 메모)를 '편집기가 가진 메모'로 써서 — 그 중 보낸 문서에 없는 것만 지우고, 그 밖에서 보낸 문서에만 있는 것만 들여온다(남이 단 메모를 지우거나 남이 지운 메모를 되살리지 않음). 없으면(옛 편집기) 기준 판의 메모(종전), 연 판의 기록 파일이 없으면 지우지 않는다.
- 서버(문서 큐 `_tx` 하나 = 기록 하나):
  1. 검사 차례(`server/live.js` `LiveEditor.push`): 404 `NO_DOC` → 실시간 문서가 아니면 409 `NOT_REALTIME` → 수정 권한이 없으면 403 `FORBIDDEN` → `base` 가 양의 정수가 아니면 400 `BAD_BASE` → 본문이 비면 400 `EMPTY`, HWPX 가 아니면 400 `BAD_FILE` → (문서 큐 안에서 방식·권한을 한 번 더) → `base` 가 지금 기록보다 크면 400 `BAD_BASE` → 기준 기록 파일(`versions/<base>.hwpx`)이 없으면 409 `STALE_BASE { baseVersion: 지금 기록 }`(웹은 §2.4-4 로 푼다).
  2. 덩어리 = `diffDocs(기준 기록 최종본, 보낸 문서)`(수정본 저장과 같은 엔진 §4.1 — 본문·표 칸·문단 추가·지움; 표 구조·개체·서식은 `unsupported` 로 알리고 반영하지 않음).
  3. 덩어리마다 지금 문서 자리로(`_refMap(기준 기록, 지금)` + `_place` — V3 §3.4 와 같은 규칙) 옮겨 글을 정한다: 지금 글 == 기준 글이면 보낸 글, 다르면 `merge3(기준 글, 보낸 글, 지금 글)`(글자 단위). **겹쳐 합칠 수 없으면 겹친 자리만 보낸 글이 이긴다**(마지막에 친 사람 — `mergePreferMine`: 보낸 편집은 모두 넣고 지금 글의 편집 중 겹치지 않은 것은 남긴다. 결과 `conflicts` 에 적고 그 문단의 지금 글을 쓴 다른 사람에게 WS `live-overwrite` 알림, §2.3). 그 문단이 지금 없으면(남이 지움) 건너뛴다(`skipped`, 이유 `GONE` — 바꿈, 그리고 넣을 자리를 찾지 못한 문단 추가; 지울 문단이 이미 없으면 할 일 없음). 옛 기준에서 다시 보낸 문서의 처리(문단 두 번 넣지 않기·같은 글 다시 보내기·기준 뒤에 넣은 문단)는 §8-3.
  4. 적용(작성자 = 친 사람 이름): 바꿈 = §2.3 의 `applyLiveText`, 문단 추가 = `insertParagraphAfter`(뒤에서부터 — V3 §3.4-4), 문단 지움 = `track: 'final'` 이면 그 본문 문단을 지운다(`removeBodyParagraph`) — 단 **글·빈 문단(표·개체·중첩 문단 없음)이고 메모가 달리지 않았고 구역 첫 문단이 아닐 때만**, 아니면 글만 지우고 빈 문단을 남긴다(메모를 앞 문단 끝으로 옮기지 못하므로). `tracked` 도 같은 조건이면 문단을 없앤다(2026-10-29): 먼저 `applyLiveText(ref, '')`(이 작성자의 처리 안 된 변경은 거둠 — 내가 넣은 문단·글이면 그것으로 끝)로 글 전체를 지우는 변경 추적을 남기고, 남은 것(지운 글·남의 변경 표식)이 있으면 그 문단을 앞 문단의 마지막 run 끝에 붙이고(`joinBodyParagraph` — 최종본은 앞 문단 그대로, 앞 문단 글자 모양 그대로, 한글 변경 추적에는 앞 문단 끝의 지운 글로 보임; 거절하면 그 글이 앞 문단 끝에 돌아온다 — **2026-10-30 부터는 붙이지 않고 아래 '문단 나눔 변경 추적'**), 없으면(빈 문단) `removeBodyParagraph`. 종전처럼 문단을 남기면 최종본에 빈 줄이 남고, 빈 문단은 남길 변경이 없어 아무것도 바뀌지 않은 채 편집기 맞추기로 지운 문단이 되살아났다. 그림·표 문단은 `final` 이면 문단째 지운다(`tracked` 는 아래 개체 변경 추적 — 2026-10-30 전에는 `tracked` 도 문단째 지우고, 그 문단에 변경 추적이 있을 때만 그림·표를 바로 지운 뒤 앞 문단에 붙였다). 조건에 맞지 않는 문단(메모·첫 문단 등)은 글만 지운다(문단은 남음).

### 2.3 실시간 글 적용(`applyLiveText(ctx, ref, target, author)`)과 기록 방식
- `track: 'final'`(고친 글만): `mergeParagraphText(ref, target, { author })` → 만든 변경을 곧바로 **수락**(`acceptChange` — 문서에는 최종 글만, 변경 추적 없음). 그 문단에 처리 안 된 변경 추적(옛 자료·승인 방식 때 것)이 있어 엔진이 `OVERLAP` 이면 그 문단의 변경 추적을 먼저 모두 수락하고 다시 한다.
- `track: 'tracked'`(변경 추적으로): 그 문단에서 **이 작성자의 처리 안 된 변경을 먼저 거절**해(이 작성자가 바꾸기 전 글로 — 문단 경계에 걸친 변경은 빼고) 놓고 `mergeParagraphText(ref, target, { author })` — 변경 추적이 언제나 '그 사람이 그 문단을 바꾼 전체'로 하나씩 남는다(타이핑마다 쪼개진 변경이 쌓이지 않게). 거절할 수 없는 내 변경(남이 내 삽입 글 안에 메모를 달아 `CTRL_INSIDE` 등)은 글 그대로 수락한다(`keepIfStuck` — 밀어 넣기가 그 문단에서 영영 막히지 않게). 다른 사람의 처리 안 된 변경과 겹쳐 `OVERLAP` 이면 그 문단의 남의 변경을 수락하고 다시 한다.
- **개체 변경은 글 규칙에서 뺀다(2026-10-30)**: 위 '이 작성자의 처리 안 된 변경을 먼저 거절'은 **글 변경만**(`changes()` 항목에 `kind` 가 없는 것) — 개체 변경(`kind: 'object'`·`'mixed'`)까지 거절하면 다음 글 밀어 넣기가 제 표·그림 지우기를 되살린다(글 합치기는 개체를 다시 지우지 않는다). `OVERLAP` 때 수락하는 처리 안 된 변경에서도 개체만의 변경(`kind: 'object'`)은 뺀다(엔진이 개체에 붙은 표식을 글 편집에서 넘기므로 겹치지 않는다). 변경 수락·거절(`resolveChange`·`acceptAll`·`_resolveIds`)은 엔진 `resolveChanges`(큰 번호부터 풀며 개체째 지울 때 안쪽 변경의 번호 밀림을 따라감)를 쓰고, 개체·섞인 변경을 풀면 서식 커밋(`ctx.formatting` — `formatVersion` 이 올라 편집기가 다시 연다)이다. 웹 변경 추적 탭은 개체 항목을 엔진 이름(`label` — '표 지움'·'그림 넣음'·같은 자리의 개체 짝은 '표 바꿈')과 `[표]`·`[그림]` 본문으로 보이고, 짝짓기(교체)는 같은 종류끼리만(글-글·개체-개체)이다. 추적으로 지운 표·그림 안(칸·캡션 — 숨은 문단 `…/dK`)의 변경은 목록·편집기 강조에서 뺀다(그 개체 변경과 함께 정해진다 — `web/menumodel.js visibleChanges`). 묶음(교체·개체 짝)은 `POST /api/docs/:id/changes/resolve { ids, mode: 'accept'|'reject' }` 한 번으로 정한다(→ `{ ok, done, gone }`, 엔진 `resolveChanges` 가 번호 다시 매김을 따라감 — 하나씩 큰 번호부터 부르면 개체째 지운 안쪽 변경 때문에 뒤 번호가 밀려 엉뚱한 변경을 정할 수 있었다; 400 `BAD_ARGS`(빈 목록·100개 넘음·mode), 404 `NO_CHANGE`(없는 번호 — 아무것도 바꾸지 않음), 403 수정 권한). 서식 덩어리의 `PENDING_TRACKED` 판정(변경 요청 반영)도 그 문단의 개체만의 변경은 보지 않는다(글자 모양 복사는 개체에 붙은 표식을 지킨다).
- **문단 나눔 변경도 글 규칙에서 뺀다(2026-10-30)**: '이 작성자의 처리 안 된 변경을 먼저 거절'은 `kind` 없는 글 변경 중 **`paraEnd` 가 아니고 `scope: 'paragraph'`(나눔이 지워진 문단의 글을 모두 지운 '지운 문단')도 아닌 것**만 — 나눔 변경을 거절하면 meta 주소를 옮기지 않은 채 최종 문단 구조가 바뀌고, 지운 문단 글을 거절하면 묶음 안 문단마다 다시 거절·다시 지우기가 되풀이된다. `OVERLAP` 때 수락하는 변경에서도 `kind: 'para'` 는 뺀다. 변경 요청 반영의 `PENDING_TRACKED`(`overlapsPending`·서식 덩어리)도 `kind: 'para'` 를 보지 않는다(묶음 안 글 편집은 나눔 표식을 넘는다). `changes()` 항목: `paraEnd: true`, `kind: 'para'`(개체가 끼면 `'object'`·`'mixed'`), `label` '문단 나눔 지움'·'문단 나눔 넣음'(한/글의 글+나눔은 '글과 문단 나눔 …'), 폭 0 나눔은 `start === end` = 그 문단 끝 자리(묶음 ref). 나눔 변경을 풀면 서식 커밋(`_touchesObjects` — 다른 편집기는 다시 연다). 웹 변경 추적 탭·우클릭 메뉴는 **'문단 지움'**(지운 나눔 + 같은 자리(ref, start)의 같은 사람의 지운 글·개체)·**'문단 넣음'**(넣은 나눔 + 다음 문단 0 부터 이어지는 같은 사람의 넣은 글·개체)을 한 묶음으로 보이고 `/changes/resolve` 한 번으로 정한다(본문 `¶지운 글` — `web/menumodel.js groupChanges`·`changeGroupLabel`·`changeText`). MCP `list_changes` 설명에 `kind "para"`.
- 두 방식 공통: `OVERLAP` 인데 그 문단에서 시작하는 처리 안 된 변경이 없으면(한글이 만든 문단 경계 변경은 앞 문단 ref 로 나온다) 문단 경계에 걸친 변경을 수락해 보고, 그대로 수락할 수 없는 변경(`SPANS_PARAGRAPH`·`CTRL_INSIDE`)은 편집기 작업본과 같은 규칙(V3 §4.3 tolerant)으로 표식만 지운다(§8-2).
- 제안·요청 쪽: 이 거절·수락으로 적용된 제안의 `changeIds` 가 없어지면 V3 의 `_syncChangeIds` 규칙 그대로 — 수락·거절 전에 그 제안에 `appliedFinal`·`appliedRange` 를 적어 두어(`_noteAppliedRanges`) 아래 §4.2 의 글 되돌리기로 복구할 수 있다.
- 덮어쓰기(§2.2-3 겹침): 덮어쓴 문단의 지금 글을 쓴 사람(그 문단의 마지막 실시간 기록의 작성자 — 서버가 `meta.liveTouch[ref] = { by, at, ins?, pushed? }` 로 최근 30분만 기억, `ins`·`pushed` 는 §8-3)에게 WS `{ type: 'doc', action: 'live-overwrite', ref, by(덮어쓴 사람), to }` — 웹은 그 사람에게만 알림 '홍길동 님이 같은 곳을 동시에 고쳐 내 글 일부가 바뀌었습니다(이력 탭에서 되돌릴 수 있음)'.

### 2.4 따라가기(서버 → 다른 편집기) — 웹 `web/editor.js`
0. 편집기 방식(`h.mode` — 열 때 문서 정보 `settings`·`canEdit` 로 정한다, `web/view.js editorMode`): `live`(실시간 문서 + 수정 권한 — 작업본을 열고 밀어 넣기), `follow`(수정 권한 없음 — **어느 편집 방식이든** 읽기 전용, 작업본을 열고 밀어 넣지 않으며 남의 고침만 맞추기로 따라감, '입력 중' 알림도 보내지 않음), `review`(승인 방식 + 수정 권한 — v0.3 그대로). 밀어 넣기(§2.2)는 이 창의 차례 `seq`(창마다 다른 시작 수 + 1씩)를 붙인다.
1. 기준이 바뀌면(WS `doc changed` — 내 밀어 넣기는 `seq` 로 가린다 — 또는 알림 없이 문단 목록이 새 판으로 바뀜) '맞춤 대기'로 둔다. **치는 중이면 기다린다**: 마지막 입력 뒤 700ms 쉬고 밀어 넣기·저장·열기·잠금·방식 바꾸기·옮겨 넣기가 없을 때 맞춘다(맞춤 대기가 8초를 넘으면 다음 쉼 400ms 에). 보내지 못한 내 글이 남아 있으면(칩 '보내지 못함') 맞추지 않는다.
2. 내 밀어 넣기 응답 뒤에는 늘 `markClean({ changeSeq: 내보내기 직전 판 })`(그새 친 글은 dirty 로 남아 다음 밀어 넣기). 응답이 `clean` 이고 새 기록이면: 새 기준 문단을 같은 판으로 읽어(`GET` 문서 정보 → `/paragraphs` → 문서 정보 — V3 §5.2-1 의 같은-버전 읽기, GET 세 번) `setBase(version, paragraphs)` 만(다시 열지 않음). 그새 판이 또 움직였거나 `clean` 이 아니면 맞춤 대기로. `skipped` 가 있으면 '이 창에서 고친 n문단은 그사이 다른 사람이 지워 문서에 넣지 못했습니다', `unsupported` 가 있으면 한 번만 '글자 모양·그림·표 구조 바꾸기는 공유 문서에 들어가지 않습니다' 알림.
3. 맞추기 — **편집기를 잠그지 않는다**(iframe inert 는 편집기 포커스를 빼 맞춘 뒤 이어 친 글이 편집기로 가지 않는다): ① 저장 안 된 내 편집이 있으면 먼저 밀어 넣고(못 보냈거나 그새 또 쳤으면 다음 쉼에) ② 지금 기준 문단을 같은 판으로 읽어 `setBase` ③ **바로 앞에서 판(changeSeq)을 다시 견줘** 그새 친 글이 있으면 기준을 되돌리고 다음 쉼에 다시(먼저 밀어 넣기), 없으면 플러그인 `syncToBase()`(§2.5 — 플러그인 안에서 한 번에 끝나 키 입력이 끼지 않는다)로 편집기 글을 기준 글로(바뀐 문단만 — 다시 열지 않음, 캐럿·스크롤 그대로) ④ `markClean` ⑤ 남이 바꾼·넣은 문단을 그 사람 색으로 밑줄(§2.4-5). 맞추지 못하면 기준을 되돌린 뒤: `BUSY` 는 300ms 뒤 다시(10번까지), 그 밖(`STRUCTURE`·`ERROR`·`READONLY`·옛 빌드 `UNSUPPORTED`, 되풀이된 `BUSY`)은 **조용히 다시 열기** — 덮개 '최신 문서로 맞추는 중…'으로 잠그고, 내 글을 먼저 밀어 넣고, 지금 선택을 기억해 다시 열고(스크롤 기억), 풀린 뒤 캐럿·선택을 새 기준 자리로 되살린다(기준 지도, 편집기 밖에 포커스가 있었으면 그대로 돌려줌).
4. 내 밀어 넣기가 409 `STALE_BASE`(기준 기록 파일이 지워짐 — 오래 쉰 창, §2.6) 또는 400 `BAD_BASE` 면 V3 §5.2-6 의 [내 글 옮겨 넣기](carryOver)를 저절로 한다: 지금 기준을 열고 이 창에서 고친 문단을 옮겨 넣은 뒤 곧 밀어 넣는다(그사이 다른 곳에서도 바뀐 문단은 덮어쓰지 않고 `[이 창에서 고친 글] …` 문단으로 — 글을 잃지 않음).
5. 다른 사람의 '입력 중'(`● 이름`) 표시는 v0.3 그대로. 맞춘 뒤 남이 바꾼 문단은 그 사람 색으로 잠깐(1.5초) 밑줄 깜빡임(플러그인 `flash` — 스크롤하지 않음)으로 보인다.
6. 실시간 문서에서는 **되돌리기(Ctrl+Z)가 내 편집만** 되돌린다: 남의 고침을 편집기에 맞춘(§2.4-3) 뒤에는 그 앞의 되돌리기 기록을 비운다(플러그인 `syncToBase` 가 고친 것이 있을 때만 함 — 스냅샷 되돌리기가 남의 글까지 되돌려 공유 문서로 다시 밀어 넣지 않게). 그래서 Ctrl+Z 는 '남의 고침이 마지막으로 들어온 뒤에 친 내 글'까지만 되돌린다. 칩 설명에 적는다.
7. 문서 설정이 바뀌면(WS `doc settings` — 웹은 받은 즉시 `canEditWith` 로 내 수정 권한을 다시 셈, 남이 바꿨으면 알림): 저장 안 된 것을 지금 방식으로 먼저 보낸 뒤(실시간 = 밀어 넣기, 승인 = 내 수정본 저장) 새 방식으로 다시 연다(실시간 ↔ 승인, 수정 권한 ↔ 읽기 전용 — 스크롤·캐럿 그대로). 밀어 넣기가 409 `NOT_REALTIME`·403 `FORBIDDEN` 이면(설정이 먼저 바뀜) 문서 정보를 다시 읽어 새 방식으로 연다 — 보내지 못한 실시간 글은 새 방식이 승인 방식이면 내 수정본으로 옮겨 넣고(carryOver), 읽기 전용이면 알린다(넣을 길이 없다). 읽기 전용 창은 밀어 넣지 않는다.
8. 상단 칩(실시간·읽기 전용): `실시간 · 저장됨 10:31` / `보내는 중…` / `보내지 못함 — [다시]`(5·10·15초 뒤 저절로 다시 — 이 창의 글은 그대로) / `읽기 전용`(수정 권한 없음 — title '이 문서의 수정 권한이 없습니다(문서 설정). 메모·AI 요청은 됩니다', 승인 방식 문서면 '— 승인 방식 문서'를 덧붙임). 실시간 칩의 title 에 Ctrl+Z 설명(§2.4-6).

### 2.5 플러그인(studio/plugin) — 더한 것(만든 그대로)
- `syncToBase()` → `SyncResult`(`studio/plugin/types.ts`):
  ```ts
  { ok: boolean,
    changed: string[],    // 글을 바꾼 본문·칸 문단 — 기준 ref, 문서 차례
    inserted: string[],   // 넣은 본문 문단 — 기준 ref, 문서 차례
    deleted: number,      // 지운 편집기 문단 수(편집기에만 있던 문단이라 기준 ref 가 없다)
    reason?: 'STRUCTURE' | 'BUSY' | 'READONLY' | 'ERROR', message?: string,
    ref?: string,         // 덧붙임: STRUCTURE 를 부른 기준 ref(있으면)
    ms?: number }         // 덧붙임: 걸린 시간(고친 것이 있을 때)
  ```
  - `ok: true` = 편집기 본문·칸 글이 setBase 로 준 기준 글과 같다('edited' 는 내지 않았고 편집기는 깨끗함). 고칠 것이 없으면 트랜잭션도 되돌리기 기록 비우기도 없이 `{ ok: true, changed: [], inserted: [], deleted: 0 }`.
  - `ok: false` 면 문서는 그대로다: `STRUCTURE` = 맞출 수 없는 구조 차이(아래 — 호스트가 다시 연다), `BUSY` = 한글 조합 중·머리말/꼬리말·각주 편집 중(잠시 뒤 다시), `READONLY` = 문서가 없음(편집기가 아직 준비 안 됨·문서가 해제됨 — 읽기 전용 설정과는 상관없다), `ERROR` = 기준(setBase)이 없음·계획이나 트랜잭션이 던짐·고친 뒤 확인 실패(studio 가 트랜잭션 전 문서로 되돌림).
  - 웹 손잡이 `d.editor.syncToBase()` 는 `changed`·`inserted` 를 지금 기준 ref 로 옮기고(짝 없으면 뺌), 옛 편집기 빌드(함수 없음)면 `reason: 'UNSUPPORTED'` 를 돌려준다.
- 계획(`align.syncPlan` — 편집 전 문서, 지금 정렬 = setBase 로 준 기준 ↔ 편집기 문서): 짝지은 본문 문단·칸 문단(표 칸·표 캡션·그림 캡션)의 글이 **정확히**(공백 무시 없이) 다르면 **글자 차이 조각**(`charOps` — 서버 `mergeParagraphText` 와 같은 조각)만 바꾼다 — 손대지 않은 글의 서식은 그대로(조각이 8개를 넘으면 앞뒤 같은 부분을 뺀 가운데 하나로). 편집기에만 있는 본문 문단은 지운다(글·빈 문단이고 컨트롤이 하나도 없을 때만). 기준에만 있는 본문 문단은 앞 짝 문단 뒤에 넣는다(글·빈 문단만 — 앞 문단 끝을 나눌 수 있으면 그 뒤(그 문단 서식), 아니면 다음 짝 글 문단 앞을 나눠서).

- `STRUCTURE`(아무것도 고치지 않음): 구역 수가 다름 · 표 격자(행·열)가 다르거나 줄이 밀림 · 칸 지도에 짝 없는 칸 문단 · 표·개체·조판 부호가 든 편집기 문단을 지워야 함 · 표·개체가 든 기준 문단을 넣어야 함 · 짝 문단이 없는 구역 · 넣을 자리를 안전하게 나눌 수 없음 · 그리고 **맞추기가 다루지 않는 글**(머리말·꼬리말·각주·글상자·그리기 개체·칸 안의 표 등 칸 지도 밖 중첩 문단)이 문서를 연 뒤 첫 setBase 때와 달라짐 — 그러면 **다시 열 때까지** 맞추기는 늘 `STRUCTURE` 다(그 글을 편집기에 들이지 못한 채 밀어 넣으면 남의 고침을 되돌리므로).

### 2.6 기록 파일 정리(GC) — 만든 그대로
- (2026-10-28 줄임 — 실시간 문서는 밀어 넣기마다 기록 파일이 하나씩 생긴다) `store.commit` 은 기록 목록(`meta.versions`)이 **30개를 넘으면** 자른다(`trimVersions`): **최근 기록** = 마지막 **30개**, 지난 **10분** 안의 기록은 **200개까지**(여럿이 한창 고칠 때 — 연결이 잠깐 끊긴 창의 기준 기록을 예전처럼 지킨다)는 그대로. 그보다 오래된 것은 **사람용 버전(v)이 붙은 기록·기록 1·묶음마다 마지막 기록**만 남긴다 — 묶음 크기는 나이에 따라 **하루 안 10분, 7일 안 1시간, 그보다 오래되면 하루(UTC)**(큰 묶음이 작은 묶음을 품어 시간이 지나며 저절로 성겨진다, `checkpointSpan`). 그런 묶음 기록(버전·기록 1 빼고)은 **400개**까지 — 넘으면 오래된 것부터 버린다(예전: 최근 200개 + 10분 묶음 2000개). 잘린 기록은 이력(`GET /history` 의 `versions`·이력 탭)에서도 빠진다.
  - 크기 어림: 1MB 문서를 오래 실시간으로 고치면 예전에는 기록 파일이 2200개(≈2.2GB)까지 쌓였다. 이제 쉬는 문서는 30 + 하루치 10분 묶음(일하는 8시간이면 ≈48) + 6일치 1시간 묶음(≈48) + 날마다 1개 + 사람용 버전 — 보통 200개 안팎, 끝까지 쌓여도 200 + 400 + 사람용 버전.
  - 정리된 기준이 되는 때: 연결된 창은 입력이 0.4~0.7초 쉬면 따라가기(§2.4)로 기준을 올리고, 따라가기에는 서버 기록 파일이 필요 없다(옛 기준 글은 창이 들고 있다). 기록 파일이 필요한 것은 **보내지 못한 글이 있는 창의 밀어 넣기**뿐이고, 그 기준이 지워지려면 그 뒤로 기록이 30개 넘게 쌓이고 **10분**이 지나야 한다(10분 안이면 200개까지 — 예전과 같음). 그 기준이 묶음 끝 기록(쉬기 직전의 마지막 기록이 대개 그렇다)이거나 사람용 버전이면 남는다. 지워졌으면 409 `STALE_BASE` → 저절로 [내 글 옮겨 넣기](글을 잃지 않음).
- 자른 뒤 `gcVersions` 가 `versions/` 폴더를 훑어 잘려 나간 기록의 파일(`versions/<n>.hwpx`)을 지운다 — 남기는 것: 목록에 남은 기록, **기록 1**, **사람용 버전**의 기록, **진행 중(draft·open)과 닫힌(closed — 다시 열 수 있다) 변경 요청의 `baseVersion`**, 그리고 **v0.4 전에 쌓인 기록**(`n < meta.gcFrom` — `gcFrom` 은 v0.4 서버가 그 문서를 처음 커밋한 기록 번호; 새 문서는 기록 2. 그래서 옛 기록 파일은 하나도 지우지 않는다). 지우다 실패해도 던지지 않는다(커밋은 그대로, 다음 정리가 다시 해 봄).
- 정리된 기록을 기준으로 둔 창: 실시간 밀어 넣기는 409 `STALE_BASE`(웹이 저절로 [내 글 옮겨 넣기], §2.4-4), 승인 방식의 수정본 저장도 404 `NO_VERSION` 이 아니라 409 `STALE_BASE`(웹은 칩 [내 글 옮겨 넣기]).
- 이력 탭(웹)은 같은 사람의 이어진 `실시간 편집` 기록(서로 5분 안, 사람용 버전이 붙지 않은 것)을 한 줄로 묶는다: `홍길동 · 실시간 편집 23번 · 10:02~10:15`(날이 바뀌면 `10-22 23:58~10-23 00:04`; 펼치면 기록마다 [내려받기]·[이 파일로 교체]). 하나뿐이면 묶지 않는다(`web/view.js groupHistory`).
- **이력 파일로 교체**는 `POST /api/docs/:id/versions/:n/restore`로 선택한 기록의 HWPX 바이트를 현재 파일과 새 버전에 저장한다. 본문·서식·쪽 구성·개체·메모·변경 추적을 선택한 파일 그대로 가져온다. 교체 직전 저장본은 이력에 남고 같은 바이트를 선택하면 버전이 오르지 않는다. 수정 권한이 필요하며, 성공 후에는 열린 실시간 편집기가 새 파일을 다시 읽는다. 교체 전에 열어 둔 파일의 자동 저장은 409 `FILE_REPLACED`로 막고, 편집기에 다시 열기 단추를 표시한다.
- (2026-10-28) **AI 작업 해결 버전의 간격**: V3 §9.4 의 `request` 사람용 버전(AI 작업이 해결되고 마지막 버전 뒤로 기준에 적용된 제안이 있을 때)은 **마지막 사람용 버전(어떤 종류든)에서 `config.documents.aiMilestoneMinutes`(분, 기본 30 — `0` 이면 예전처럼 해결마다, 숫자가 아니거나 음수면 30)가 지났을 때만** 만든다(`service._txMilestone`·`_aiMilestoneMs`). 그 전에 해결된 AI 작업의 적용은 기록으로만 남고 다음에 생기는 버전에 함께 담긴다 — 그래서 `request` 버전의 note 는 마지막 버전 뒤로 기준에 적용된 제안이 있는 **해결된 요청 모두**와 그 적용 수의 합이다(`AI 작업 #1·#2 해결 — 적용 3건`; 아직 해결되지 않은 요청의 적용도 내용에는 들어가지만 글에는 넣지 않는다). 시각을 읽을 수 없는 옛 이정표는 지난 것으로 본다. [버전 저장]·복구·편집본 올림·변경 요청 반영의 버전은 간격과 상관없이 그대로 만든다. 시간이 지나 저절로 버전이 생기지는 않는다(다음 AI 작업 해결이나 [버전 저장] 때).

### 4.2 반영·되돌리기(실시간 문서)
- [모두 반영] = 서버 `resolve { apply: 'rest' }`, 하나 반영 = `POST /proposals/:pid/apply`, [남은 n건 거절] = `resolve { reject: 'rest' }` — 실시간 문서에서는 **수정 권한이 있으면 '기준에 바로 적용' 문이 열린다**(§4.3). 반영하면 WS `doc changed` 로 모든 편집기가 §2.4 로 따라간다(요청자의 편집기도 — applyBatch·adopt 를 쓰지 않는다).
- `track: 'final'` 문서의 적용(`_applyCore`)은 만든 변경을 곧바로 수락한다(문서에는 최종 글만). 그 제안의 되돌리기(`undo`)는 **글 되돌리기**: 바꿈 제안은 그 문단에서 적용한 글(`p.replace`)을 원래 자리(적용 때 적어 둔 `p.appliedRange = { ref, start, end, pre, post }` — 그 뒤 글이 바뀌었으면 가장 가까운 같은 글; 지우기 제안은 앞뒤 글 `pre`·`post` 로 자리를 찾음)에서 찾아 원문(`p.find`)으로 바꾸고 수락, 문단 추가 제안은 넣은 문단 글이 그대로면 그 문단을 지움(메모가 달렸으면 글만 지우고 빈 문단을 남김, 그새 고쳐졌으면 409 `STALE`), 표 제안은 넣은 표 문단(+캡션) 지움(v0.3 그대로). 찾지 못하면 409 `STALE`('그 뒤 그 자리가 다시 고쳐져 되돌릴 수 없습니다 — 이력 탭에서 그 시점으로 복구하세요'). 대상 문단이 통째로 지워진 제안은 §8-4. `tracked` 문서는 v0.3 그대로(변경 거절 — 그 변경이 이미 수락·거절되었으면 글 되돌리기, §8-8).
- 승인 방식 문서는 v0.3.1 그대로(내 수정본에 반영 → 변경 요청).
- (2026-10-30) 표·그림 제안의 적용: 변경 추적으로 남기는 문서(실시간 '변경 추적으로'·승인 방식)는 넣은 표·그림도 '표 넣음'·'그림 넣음' 변경(작성자 = 제안자, 제안 `changeIds` 에 캡션 제목 변경과 함께)이다. '고친 글만'은 종전대로 곧바로 수락. 되돌리기는 어느 방식이든 그 표·그림 문단째 지운다(그림 파일도 거둠). 그림 교체(`figure.replace` — 그 자리 그림의 파일·크기만 바꿈)는 개체 고침이라 종전대로 추적하지 않는다(옮김·크기와 같은 규칙).
### 4.3 '기준에 바로 적용' 문(`_canDirectApply(user, meta, agent)`)
- 실시간 문서: `canEdit(user, meta)`(에이전트면 + `config.allowAgentApply`). 승인 문서: v0.3 그대로(관리자 또는 `allowDirectApply`, v0.2 설정 예외 포함). REST `/proposals/:pid/apply`·`POST /proposals {applyNow}`·`resolve {apply}`·MCP `apply_proposal`·`PUT /upload` 모두 이 문. `routes/collab.js` 의 문(gate)은 문서 meta 를 읽어 이 함수를 부른다.
- 수정 권한이 없는 사람은 실시간 문서에서도 반영·거절을 못 한다(403 `FORBIDDEN` — 거절도 문서를 정하는 일). 자기 요청이어도 마찬가지(요청은 할 수 있음).
- 문이 닫혔을 때의 오류(`_directApplyDenial`, 이 차례로): 에이전트 적용이 꺼짐(`allowAgentApply: false`) → 403 `FORBIDDEN` · 수정 권한 없음(실시간 문서, 또는 승인 문서에서도 권한 없는 사람) → 403 `FORBIDDEN` · 승인 문서의 관리자 전용 → 403 `DIRECT_APPLY_FORBIDDEN`(v0.3 그대로).
### 4.4 AI 작업 메모(`aiMemo`)
- `summary`(기본): `[AI 작업 #2] 홍길동 · 처리 Claude Code` / 요약 한 문단(`r.summary`, 줄바꿈은 그대로 두되 600자까지) / 결과 한 줄 `결과: 반영 14건 · 의견 1건 · ✓ 해결 10-23 01:16`(해결 전이면 `· 남은 제안 2건`, 결과가 없으면 V3 §9.3 의 결과 줄 규칙) — 반영 목록·이력 줄은 없다. 답글 블록은 그대로.
- `detail`: v0.3.1 §9.3-3 꼴 그대로.
- `summary`의 새 메모는 완료·부분 결과·공유 요약부터 만든다. 내용 없는 pending·working·failed·cancelled은 AI 작업 탭에서만 확인한다.
- `none`: 새 자동 작업기록 메모를 만들지 않는다. 기존 기록 메모·사람 답글·AI 확인 의견은 보존하며 기록은 AI 작업 탭에서 확인한다.

## 8. 정한 것(구현·검토에서, 2026-10-23)
위 글이 둘로 읽히던 곳·구현과 검토에서 정한 것(시험이 이대로 본다). 앞 절과 다르면 이 절이 이긴다.

**서버**
1. **설정 기본값**(`_settingDefaults`·`_normSettings`): `editMode` = `config.documents.defaultEditMode`, `track` = `defaultTrack`, `exportKind` = `defaultExportKind`, `aiMemo` = `defaultAiMemo`, `aiQuick` = `defaultAiQuick` — 모두 서버 config 만의 키이고(문서 설정 창에는 없음) 없거나 모르는 값이면 `realtime`·`final`·`final`·`summary`·`send`, `editors` 는 언제나 `'all'`. 사용자 config 에는 `documents` 구역이 없다 → 기본은 실시간·편집자 모두·고친 글만·보이는 그대로·요약(`config.example.json` 은 `"documents": { "defaultEditMode": "realtime" }`). 새 문서는 올릴 때의 기본값을 meta 에 적어 둔다(그 뒤 config 가 바뀌어도 그대로). 설정이 없는 옛 문서는 읽을 때마다 지금 기본값으로 채우고 그 문서의 meta 가 처음 저장될 때 적힌다. `PATCH /settings` 는 모르는 키를 건너뛰고(아는 키가 하나도 없으면 400 `BAD_SETTING`), 바뀐 것이 없으면 기록·WS 없이 `{ settings }`.
2. **수정 권한이 있어야 하는 일**(403 `FORBIDDEN`, 어느 편집 방식이든): 밀어 넣기, 제안 적용('기준에 바로 적용' 문 §4.3)·거절·되돌리기·다시 열기, 요청 일괄 해결(resolve — adopt·apply·reject 모두), 변경 추적 수락·거절·모두 수락, 버전 복구, 변경 요청 반영·다시 열기·검토 요청, 수정본 저장·버리기·다시 맞추기, 내 수정본에 반영 기록(adopt). 메모·답글·해결·AI 요청은 권한 없이도 된다.
3. **옛 기준에서 다시 보낸 문서**(편집기는 치는 동안·clean 이 아닌 응답 뒤 맞추기 전에는 기준을 옮기지 않는다, 응답을 못 받은 재시도도 같은 고침을 또 담는다 — `server/live.js`): `meta.liveTouch[ref]` 에 `ins = { by, base, text, v }`(실시간으로 넣은 문단 — 넣은 사람·그때 편집기 기준·마지막에 보낸 글·넣은 기록)와 `pushed[사람] = { base, ref: 기준 ref, h: 보낸 글 지문 }`(30분, 문단 넣기·지우기를 따라감)을 적어 ① 보낸 사람의 기준 뒤에 넣은 문단은 기준 → 지금 짝짓기에서 뺀다(planBody 가 그 문단을 이미 지워진 기준 문단의 짝으로 잡아 지우거나 덮어쓰지 않게) ② 같은 창이 같은 기준에서 넣은 문단은 **다시 넣지 않고** 그 문단에 맞춘다(문단이 두 번 들어가지 않음) ③ 같은 기준에서 **같은 글을 다시 보낸 문단은 건너뛴다**(멱등 — 그새 남이 바로 옆에 친 글이 지워지지 않게; 같은 글인지만 보므로 같은 사람의 다른 창이어도 틀리지 않는다). 남는 한계: 옛 기준 창이 자기가 앞서 보낸 고침을 되돌리거나 자기가 넣은 문단을 지우면 그 되돌림은 실리지 않는다(창 id 가 없다 — 맞춘 뒤 다시 고치면 된다).
4. **통째로 지운 문단을 가리키던 제안**: `_remapRefs` 가 표시한다 — 대기 제안은 `lost`(적용 → 409 `GONE`), 적용·거절·복구된 것은 `refGone`(글 되돌리기는 409 `STALE`, 다시 열면 `lost` → 적용하면 `GONE`), 넣은 문단이 지워진 문단 추가 제안은 `insertedGone`(되돌리기 409 `STALE` — 그 번호의 다른 문단을 지우지 않게).
5. **변경 요청 반영(실시간 문서)**: 승인 없이·수정 중(draft)도(작성자·관리자 + 수정 권한). '고친 글만' 문서에서는 ① 덩어리가 겹치는 처리 안 된 변경 추적(`PENDING_TRACKED`)을 그 대상 문단 것만 먼저 수락하고 다시 놓는다(반영이 다른 까닭으로 막히면 `_tx` 가 이 수락도 함께 버린다) ② 반영이 만든 변경은 곧바로 수락 ③ 반영으로 적용된 제안은 모두 `appliedFinal`(제 변경 id 를 가려내지 못한 것도 — 글 되돌리기로 복구). 그래서 실시간 '고친 글만' 문서의 CRView 는 `PENDING_TRACKED` 로 막지 않는다. '변경 추적으로' 문서의 반영은 v0.3 처럼 변경 추적으로 남는다.
6. **'고친 글만' 문서에서 곧바로 수락하는 것**: 실시간 글, 제안 적용, 변경 요청 반영, 편집본 올리기(`PUT /upload`), 버전 복구(겹쳐 못 맞추면 문서의 처리 안 된 변경 추적을 **모두** 먼저 수락하고 다시) — 문서에 변경 추적이 새로 남지 않는다. 실시간 문서에서 변경 추적을 수락·모두 수락하면(웹 '자세히'의 변경 추적 탭) 그 변경을 가진 적용된 제안은 글 되돌리기 표시를 받는다.
7. **문단 경계 변경**(한글이 만든 `SPANS_PARAGRAPH`) — 밀어 넣기를 막을 때만 너그럽게 수락한다: 그 문단에서 시작하는 처리 안 된 변경이 없어 `OVERLAP` 이 풀리지 않으면 문서의 문단 경계 변경을 수락해 보고(고친 글만 = 모두, 변경 추적으로 = 남의 것), 그대로 수락할 수 없으면 표식만 지운다(`_acceptLoose` — 글은 최종본대로).
8. **'변경 추적으로' 문서**: 내 처리 안 된 변경 중 거절할 수 없는 것(`CTRL_INSIDE` 등)은 글 그대로 수락한다(`keepIfStuck` — 밀어 넣기가 막히지 않게). 적용된 제안의 변경(작성자 = 제안한 사람)을 그 사람의 실시간 글이 거절·다시 쓰면 그 제안은 글 되돌리기로 복구된다.
9. **aiMemo** 는 다음에 그 요청을 다시 셀 때(제안을 정하는 등) 새 꼴로 다시 쓴다 — `PATCH /settings` 가 메모를 다시 쓰지는 않는다. 요약 꼴에서 반영한 것이 없고 남은 것도 없으면 결과 줄은 `반영한 제안 없음`.
10. **기록 파일 정리**: §2.6 — 닫힌 변경 요청의 기준도 남긴다(다시 열면 그 기록을 읽는다), 승인 방식 수정본 저장도 정리된 기준이면 409 `STALE_BASE`.
